# Buildin → табло: рабочая схема

## Обновление

После подтверждённой отметки Selectel вызывает только workflow `buildin-board.yml` этого репозитория, ветку `main`, с `publish: true`. При включённых карточках передаётся `notice_event` — стабильный хеш ID события. Получатель, текст и URL из бота в GitHub не передаются.

GitHub заново читает обе таблицы Buildin, проверяет полноту ответов и соответствие схем, объединяет поддерживаемые события с исходной историей в `index.html`. Новые участники требуют корректного сопоставления с табло. Неоднозначные сопоставления останавливают публикацию. Даты выхода на трек, пит-стопы и исходная история сохраняются; исправление исторической отметки в исходном HTML требует отдельной сверки.

Вторая возможность — расписание **09:07 и 21:07 по Москве**: `7 6,18 * * *` UTC. Оно подхватывает ручные изменения в Buildin. Расписание не отправляет личные сообщения. Запуски и публикация могут задерживаться; запрос обновления ещё не означает его завершение.

В Actions → Buildin → табло → Run workflow ручной запуск с `publish: false` создаёт предварительный результат без публикации. `notice_event` вручную оставляют пустым.

## Настройки GitHub

| Где | Имя | Назначение |
|---|---|---|
| Repository secret | `BUILDIN_API_TOKEN` | Чтение двух таблиц сборщиком |
| Repository variable | `BUILDIN_SYNC_ENABLED=true` | Включение расписания |
| Environment secret, `github-pages` | `NAVIGATOR_TELEGRAM_BOT_TOKEN` | Отправка сообщения после публикации |
| Environment secret, `github-pages` | `NAVIGATOR_ADMIN_TELEGRAM_ID` | Единственный личный получатель |

В `github-pages` разрешена ветка `main`. Пустой раздел Environment variables нормален. Значения секретов не вставляют в код, issue, логи или документацию. Код workflow и отправителя должен оставаться под контролем владельца: возможность менять исполняемый код означает возможность использовать доступные ему секреты.

Права сборки: `contents: read`. В управляемом режиме отдельное задание сохранения истории получает `contents: write` и `actions: read`; оно использует служебный GitHub-токен и фиксированную ветку `tablo-participants-state`. У задания публикации дополнительно `pages: write` и `id-token: write` для GitHub Pages. Actions закреплены SHA. Сборка получает только Buildin-токен; два Telegram-секрета получает только шаг уведомления после публикации.

## Настройки Selectel

Основные параметры пульта хранятся в закрытом `/etc/navigator/bot.json`. Полную схему установленной версии сверяем с памяткой Selectel:

| Имя | Назначение |
|---|---|
| `ADMIN_TELEGRAM_ID` | Владелец пульта |
| `BUILDIN_PARTICIPANTS_DATABASE_ID` | Таблица участников |
| `BUILDIN_DATABASE_ID` | Таблица событий |
| `TELEGRAM_BOT_TOKEN` | Получение и ответы Telegram |
| `BUILDIN_API_TOKEN` | Чтение, запись событий и подтверждение связей |
| `BUTTON_SIGNING_SECRET` | Подпись подтверждающих кнопок |
| `GITHUB_DISPATCH_TOKEN` | Запрос запуска workflow только нужного репозитория |
| `TABLO_SYNC_ENABLED=true` | Быстрый запрос обновления после отметки |
| `TABLO_CARDS_ENABLED=true` | Запрос личной ссылки после публикации |

Для отправки сигнала GitHub используется fine-grained token с доступом только к этому репозиторию и `Actions: write` (Metadata: read предоставляется GitHub). Он не хранится в открытом репозитории. Фактические права и срок действия токена проверяют в настройках аккаунта.

## Что считать успешным

1. Бот подтвердил существующую или сохранённую запись и связь в Buildin.
2. Workflow прошёл проверки и публикацию.
3. Отправитель подтвердил нужное событие именно в опубликованном выпуске: `PUBLICATION_VERIFIED`.
4. Telegram подтвердил карточки и меню: `TELEGRAM_DELIVERED`, `TELEGRAM_MENU_DELIVERED`.

Успех публикации отдельно не доказывает доставку сообщения. Сбой уведомления не отменяет публикацию и не повторяет запись Buildin. Подробности — в `PERSONAL-LINKS.md`.

## Управление участием через Buildin

Поля, первый перенос, подтверждение изменений и повторные пит-стопы описаны в [PARTICIPANTS.md](PARTICIPANTS.md). Режим включается переменной `BUILDIN_PARTICIPANT_MANAGEMENT=true` после предпросмотра. Сборщик только читает Buildin, служебная ветка хранит принятые профили и все паузы. Её запись и проверка предшествуют публикации Pages. После первого переноса отключение этого режима останавливает публикацию, чтобы прежняя программа не затёрла накопленную историю.
